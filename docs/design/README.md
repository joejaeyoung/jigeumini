## 핵심 결정

- Java 21을 초기 기준으로 삼고, 구현 시 지원되는 Spring Boot 정식 버전과 BOM 호환성을 확인해 버전을 고정한다. Kafka·PostgreSQL 이미지도 정식 릴리스의 명시적 태그로 고정한다. `latest`에 의존하지 않는다.
- 수집기, 분석기, 조회 서버는 같은 저장소의 Spring Boot 애플리케이션으로 구현한다. 분석기는 실행 프로필을 달리해 순위·급증 소비자를 독립 실행한다.
- 2026-10-25 확정 디자인 이후 서버·웹 모노레포로 전환한다. 서버는 Spring, 제품 웹은 React·TypeScript·Vite이며 HTTP API로 연결한다. 초기 Spring 정적 운영 화면은 보존한다. [개발 구조](../DEVELOPMENT.md)를 따른다.
- Kafka는 입력 보관·독립 소비·재처리를 담당한다. PostgreSQL은 메타데이터·멱등 처리 기록·집계·조회 결과를 담당한다.
- MVP는 일반 공개 방송 2~3개 PoC 후 **선정한 최대 20개 채널**을 목표로 한다. 실제 지원 수는 실측 결과로 결정한다. 전체 치지직 순위라고 표시하지 않는다.
- 채팅 원문·닉네임·사용자별 순위는 MVP 범위에서 제외한다. 채팅 발생 이벤트를 세는 데 필요한 필드만 Kafka에 발행한다.
- 외부 채팅 수신부터 DB까지의 무손실·exactly-once를 주장하지 않는다. 동일 내부 이벤트 ID의 DB 재반영은 방지한다.
- 비공식 수집 성공 여부가 첫 번째 진행 조건이다. 실패할 경우 제한 우회가 아닌, 협력 채널의 공식 API 연동 또는 데이터 소스 재검토로 전환한다.

## 구현 순서

1. **M0 수집 PoC:** 익명 수신·메시지 구분·재접속·수신량 확인.
2. **M1 수직 구현:** 1개 채널 → Kafka → PostgreSQL → 화면까지 연결.
3. **M2 제품 기능:** 1분/5분 순위, 추이, 급증, 수집 상태 표시.
4. **M3 신뢰성:** 중복·장애·DLQ·재처리 실험.
5. **M4 성능 검증:** 별도 합성 입력으로 부하·복구 측정, 결과 보고서 작성.

일정은 개발 가능 시간과 M0 결과 확인 후 산정한다. 새로운 기능보다 위 순서의 통과 조건을 우선한다.
