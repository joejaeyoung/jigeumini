정제 결과: [30분 JSON](evidence/live-soak-30m.json), [메모리 관측](evidence/soak-resources.csv), [실행 메타데이터·JAR SHA-256](evidence/execution-metadata.json).
30초 간격 자원 표본 53개에서 RSS는 111.7~311.4MiB였다. 프로세스 시작 직후부터의 연속 peak 측정은 아니며 이 표본으로 누수 부재·최대 처리량을 주장하지 않는다.
JVM heap은 이번 장기 실행에서 별도 제한하지 않았고 실제 VM flags를 메타데이터에 남겼다.

장기 관측 중 최종 코드에 숫자 범위 검증, 승인 실패 시 통계 정리, 종료·중복 실행 진단과 진행 로그를 보완했다.
따라서 장기 실행 JAR와 최종 JAR의 hash를 구분한다. 최종 JAR도 별도 60초 실방송·30초 강제 재접속으로 확인했다:
[최종 JAR 스모크](evidence/final-live-smoke-60s.json), 2026-10-25 13:59:44~2026-10-25 14:00:44 KST, PASS.


## 로컬 자동 검사

프로토콜·HTTP·WebSocket 테스트 20개 통과. 실방송 의존 없이 실행했다.
`./scripts/check`로 테스트·실행 JAR 빌드·문서 링크 검사를 통과했다.
개별 suite 결과: [로컬 테스트 요약](evidence/local-tests.json). GitHub 원격 CI는 실행하지 않았다.

## 중복 실행 방지

30분 수집 프로세스가 동작하는 같은 저장소 루트에서 두 번째 JAR를 실행했다.
새 연결 전에 종료 코드 2와 중복 실행 거부 메시지를 반환했고 결과 파일을 만들지 않았다.

## 해석 범위

실제 공개 채널에서 수신 경로를 확인한 결과다. 원천 누락률, upstream 중복 제거, 차단 시 복원,
외부 서비스의 지속 가용성, Kafka·DB 정합성, 상시 20채널 운영 성능은 검증하지 않았다.
