# Chat Pulse — PRD

2026-10-25 · v0.2 · 상태: 구현 전 초안

## 1. 제품 정의

**선정한 치지직 방송 중 지금 채팅 반응이 활발하거나 급증한 방송을 찾는 실시간 분석 서비스.** 방송별 최근 채팅 수, 순위 변화, 시간별 추이와 데이터 수집 상태를 함께 제공한다.

시청자 수만으로는 반응이 집중되는 순간을 알기 어렵다는 가설에서 출발한다. 채팅 수는 관심·활동의 보조 지표이며 긍정 반응, 만족도, 고유 시청자 수를 의미하지 않는다. 제품 가설은 실제 시연과 사용자 피드백으로 검증한다.

## 2. 사용자와 사용 흐름

| 사용자 | 원하는 일 | 제공할 결과 |
|---|---|---|
| 방송 시청자 | 지금 반응이 활발한 방송 찾기 | 최근 1분/5분 채팅량 순위와 원본 방송 링크 |
| 방송 시청자 | 평소보다 반응이 급증한 방송 찾기 | 급증 피드와 판단 근거 |
| 프로젝트 운영자 | 수집이 멈춘 방송 구분 | 연결·지연·누락 가능 구간 표시 |
| 프로젝트 개발자/리뷰어 | 설계가 실제로 동작하는지 확인 | 장애 복구·재처리·부하 실험 결과 |

주요 흐름: 메인 순위 → 방송 상세 추이 → 급증 시점 확인 → 해당 방송 열기. 운영 화면은 별도 인증을 적용하고 채널 등록, 수집 중지, 실패 상태 확인을 제공한다.

## 3. 목표와 비목표

### 목표

1. 실제 외부 채팅 이벤트로 실시간 순위를 갱신한다.
2. 서로 다른 분석기가 같은 Kafka 입력을 독립적으로 소비한다.
3. 수집 중단·처리 지연을 숨기지 않고 결과의 범위를 보여준다.
4. 동일 입력 재처리 시 집계가 변하지 않는다는 것을 통합 실험으로 확인한다.
5. 처리량·지연·복구 시간을 측정해 이력서와 기술 문서에 재현 가능한 근거를 남긴다.

### MVP에서 제외

- 치지직 전체 방송을 빠짐없이 수집한다는 보장.
- 연령·로그인·구독 등 접근 제한 우회.
- 채팅 송신, 방송 관리, 후원·구독 이벤트 집계.
- 닉네임/사용자 추적, 개인별 채팅 순위, 원문 공개 검색.
- AI 감정 분석, 인기 키워드, 자동 영상 편집, 외부 메시지 알림.
- Kubernetes, Redis, Elasticsearch, Kafka Streams 도입. 필요가 실측되면 후속 결정한다.

## 4. 기능 요구사항

| ID | 우선순위 | 요구사항 | 수용 기준 |
|---|---|---|---|
| FR-01 | P0 | 수집 채널 관리 | 관리자가 채널 ID를 등록·중지할 수 있다. 일반 공개 방송 여부를 확인한다. |
| FR-02 | P0 | 실시간 일반 채팅 수집 | 일반 채팅만 COUNT 대상으로 정규화한다. 후원·시스템·최근 이력은 구분하고 제외 이유를 기록한다. |
| FR-03 | P0 | 1분/5분 채팅량 순위 | 정의된 시간 구간의 수신 이벤트 수와 순위, 기준 시각, 대상 수를 표시한다. |
| FR-04 | P0 | 순위 변화 | 동일 window와 비교 가능한 직전 60초 기준 snapshot 대비 순위 변화를 표시한다. 비교 대상이 없으면 신규/비교 불가로 표시한다. |
| FR-05 | P0 | 방송별 추이 | 최근 1시간의 분 단위 채팅 수와 수집 불완전 구간을 표시한다. |
| FR-06 | P0 | 급증 감지 | 기준선·최소 건수·증가율을 모두 만족한 경우만 피드에 기록하며, 동일 방송의 반복 기록을 제한한다. |
| FR-07 | P0 | 수집 품질 표시 | 중단을 채팅 0건으로 표시하지 않는다. 수집 상태·집계 갱신 시각·지연을 제공한다. |
| FR-08 | P0 | 재처리 | 보존된 Kafka의 고정 offset 범위를 별도 run으로 재집계하고, 동일 입력의 기대 결과 또는 완료된 기준 run과 비교한다. 운영 결과를 직접 덮어쓰지 않는다. |
| FR-09 | P0 | 실패 이벤트 관리 | 분석별 DLQ에 사유와 원본 위치를 기록한다. 수정한 로직은 원본이 남아 있는 범위를 새 replay run으로 검증한다. 운영 run으로의 DLQ 재투입은 MVP에서 제외한다. |
| FR-10 | P0 | 운영 관측 | 연결 수, 수신량, 발행 실패, 버퍼, lag, 중복, DLQ, 지연을 확인한다. |
| FR-11 | P1 | 수집 규모 확대 | 20개 초과는 호출·접속 안정성과 저장량 검증 후 확대한다. |
| FR-12 | P1 | 키워드 분석 | 원문 처리 범위와 보존 정책을 별도로 정한 후 독립 소비자로 추가한다. |

P0가 MVP 완료 범위다. P1은 MVP 완료 조건이 아니다.

## 5. 집계와 화면 규칙

### 시간 구간

- 내부 저장은 UTC, 화면 표시는 Asia/Seoul로 한다.
- 기준 시각 T는 현재 시각을 10초 경계로 내림한 값이다.
- 1분 순위는 `[T−60초, T)`, 5분 순위는 `[T−300초, T)`의 **이벤트 발생 시각**으로 집계한다. 최종 0~9초는 다음 갱신에서 포함된다.
- UI 조회 주기는 5초다. 집계 창 경계·10초 snapshot 생성·화면 polling에 따른 표시 지연이 추가되므로, 아래 DB 반영 p95 3초 목표를 화면 표시 3초 보장으로 해석하지 않는다. 발행된 순위 snapshot의 건수·순위는 고정하며, 사후 발견한 수집 공백은 품질 표시를 하향 정정한다. 늦게 처리된 이벤트는 다음 snapshot의 해당 시간 구간과 과거 추이에 반영될 수 있다.
- 동률이면 채널 ID 오름차순으로 정렬해 재현성을 확보한다. 순위는 이 정렬 기준의 순번이다.
- 최근 채팅 이력은 MVP 실시간 순위에 더하지 않는다. 발생 시각이 잘못된 이벤트는 격리한다.

### 수집 품질

- 기본 순위는 구간 내 heartbeat로 추정한 연결 정상 시간이 95% 이상이고, 알려진 손실·미해결 격리 오류가 없으며, 미발행 버퍼와 분석 freshness가 각각 10초 이내인 채널만 포함한다. 이 95%는 **채팅 수신율이 아닌 연결 시간 커버리지**다.
- 나머지 채널은 ‘수집 불완전/집계 지연’ 영역에 표시한다. 중단 구간은 차트에서 빈 구간으로 그린다. 정상 연결에서 받은 채팅이 없으면 0건으로 표시하고, 불완전한 구간의 수신 건수는 참고값으로만 제공한다.
- 정상 연결이어도 플랫폼이 보내지 않은 메시지는 감지하지 못할 수 있다. 제공 수치는 ‘수집한 일반 채팅 수’다.
- 순위 변화는 두 시점 모두 정상 수집이 확인된 채널만 수치화한다. 다른 채널의 추가·제외로 변할 수 있음을 설명한다.

### 급증 감지 v1 — 검증할 초기 정책

- 최근 완료 1분 건수 C와 그 이전 5분의 분당 평균 B를 비교한다.
- `C ≥ 100`, `C − B ≥ 50`, `C / max(B, 10) ≥ 2`를 모두 만족해야 한다.
- 정확히 10초 간격의 연속 두 평가에서 만족하면 한 번 기록한다. 조건 불충족·품질 불량·평가 누락은 연속 횟수를 초기화한다. 채널별 cooldown은 5분이며, cooldown 중에는 연속 횟수를 쌓지 않는다.
- 비교에 필요한 6분의 커버리지와 분석 freshness가 충족되지 않으면 판단을 보류한다. 0건 구간도 연결이 정상이면 기준선에 포함한다.
- 초기 수치는 제품 정책 후보다. 표본을 보고 조정하고 algorithmVersion을 남긴다.
- 늦은 이벤트는 과거 그래프를 수정할 수 있지만 과거 시점의 급증을 뒤늦게 사용자 피드로 발송하지 않는다.

## 6. 화면 범위

1. **메인:** 1분/5분 토글, 채팅 수, 순위 변화, 상태, 기준 시각, 수집 대상 수.
2. **방송 상세:** 제목·방송 링크, 최근 1시간 추이, 급증 이력, 수집 공백.
3. **급증 피드:** 발생 시각, C/B/증가율, 알고리즘 버전. 투자·인기·만족도 같은 다른 의미로 해석하지 않는다.
4. **운영 화면:** 채널 관리, 연결·버퍼·lag·DLQ 상태, 재처리 실행 현황. Kafka/DB 용어는 일반 사용자 화면에 노출하지 않는다.

## 7. 초기 검증 목표

다음은 **아직 달성하지 않은 테스트 목표**다. 실제 장비의 CPU·메모리·디스크, JVM 설정, DB 풀, 파티션/소비자 수를 결과에 함께 기록한다.

| ID | 항목 | 초기 합격 기준 |
|---|---|---|
| NFR-01 | 실제 소스 검증 | 일반 공개 채널 2~3개를 30분 수신하고 재접속 시험을 기록한다. 채팅이 없던 구간을 접속 실패로 단정하지 않는다. |
| NFR-02 | 합성 지속 입력 | 20개 가상 채널 합계 500 events/s, 10분 입력. 유효 Kafka 확인 입력의 고유 eventId 수와 각 분석기의 반영 건수가 일치한다. |
| NFR-03 | 처리 지연 | NFR-02에서 수집/생성 시각→DB 반영 지연 p95 ≤ 3초. late/invalid/duplicate 분포를 별도 기록한다. |
| NFR-04 | 조회 | 20채널·최근 1시간 데이터, 동시 조회 20개에서 API p95 ≤ 300ms. |
| NFR-05 | 소비자 복구 | 순위 소비자 60초 중지 후 재개, 지속 입력 500/s에서 180초 안에 지연이 정상 기준으로 돌아온다. 급증 소비자는 계속 동작한다. |
| NFR-06 | 멱등성 | 동일 eventId의 중복 발행 및 DB commit 직후 소비자 종료 후에도 최종 bucket 합계가 기준과 일치한다. |
| NFR-07 | 재처리 | 고정 start/end offsets의 테스트 입력을 새 run으로 처리했을 때 채널·10초 bucket별 건수가 기준 결과와 일치한다. |
| NFR-08 | 과부하 | 2,000 events/s 60초 입력 시 메모리 한도·손실 정책이 지켜지고 lag와 회복 시간을 보고한다. 지연 목표 달성은 요구하지 않는다. |

500/s를 24시간 운영할 수 있다는 뜻이 아니다. 실방송 처리량과 합성 부하 결과는 분리해 발표한다. 실제 소스 연결을 늘려 부하를 만들지 않는다.

## 9. 리스크와 결정 대기

- **미검증 접속:** 소스 구현 존재만 확인했다. M0 전에는 현재 수신 성공을 가정하지 않는다.
- **비공식 변경:** 수집 어댑터를 분리하고 프로토콜 파싱 fixture를 남긴다. 제한 우회나 전체 플랫폼 부하 시험은 범위 밖이다.
- **원천 중복/누락:** 플랫폼 고유 ID와 재개 기능은 미확인이다. 내부 eventId 멱등성과 원천 정합성을 구분한다.
- **수집기 장애:** 메모리 버퍼의 미확인 이벤트는 잃을 수 있다. UI에 공백을 표시한다. 디스크 spool은 후속 설계다.
- **관측 한계:** 연결 커버리지 100%는 원천 메시지 수신율 100%가 아니다.
- **데이터 보존:** 원문과 사용자 식별정보는 MVP에 저장하지 않는다. 확장 시 목적과 이용 조건에 맞춰 재설계한다.
- **소규모 필요성:** 이 규모에서 Kafka가 유일한 해법은 아니다. 채택 근거는 독립 소비·보존·재처리를 실제로 검증하는 데 있다.
