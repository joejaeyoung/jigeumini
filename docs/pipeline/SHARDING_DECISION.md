# 방송 내부 샤딩: 현재는 도입 보류

2026-10-27 · [#68](https://github.com/joejaeyoung/jigeumini/issues/68) · 기준 `cca9877`.
F01/F05/F06/F08/F10 → T02/T04/T06/T07/T08. 진행 상태와 완료 게이트는 [STATUS](../STATUS.md)가 정본이다.

## 결정

**현재 제품은 공용 채팅 토픽 P3, channelId 키 S1, group별 consumer 1명을 유지한다.** 방송 내부 S3의 제품 도입은 보류한다. 여기서 P는 토픽 partition 수, S는 방송 한 곳이 사용하는 shard 수, C는 같은 group의 consumer 수다.

#67의 C3 반복에서 실제 분산과 단순 집계 지연 개선을 확인했다. #65에서는 SQL 비용을 줄인 기존 S1 제품이 현재 복합 비교 후보를 다시 통과했다. 전체 제품의 병목이 인기 방송 한 partition의 직렬 소비라는 증거와, 제품 S3가 같은 자원에서 주는 이득은 아직 없다. 품질·보정·복구 계약을 바꾸는 비용을 감수할 근거가 부족하므로 도입을 보류한다. 샤딩이 전체 제품에서 느리다고 확정한 결정은 아니다.

#68의 “#65 결과상 이득이 없거나 복잡성 대비 가치가 없으면 이유·재개 조건을 기록하고 제품 기본값을 유지”하는 분기를 선택한다. 아래의 제품 구현·장애·부하 항목은 **채택을 다시 검토할 때 충족할 조건**이다. 실행하지 않은 체크리스트를 통과 처리하지 않는다. T07은 단순 집계 실험 범위의 부분 검증을 유지한다.

기존 suffix `sharded-3`는 hot 방송이 한 partition에 남았으므로 샤딩 개선 근거에서 제외한다. 단순 실험 개선율을 600채널 또는 복합 후보의 처리량에 곱하지 않는다. 공용 토픽 P3과 방송별 토픽 생성도 별개다. S3는 총 입력·보존 bytes·RF를 줄이지 않는다.

## 다시 검토할 조건

다음 중 하나가 생기면 #68을 다시 열고 입력·자원·판정 기준을 고정한 실험을 시작한다.

1. 실제 목표 입력 또는 재현 가능한 합성 목표에서 기존 제품이 SLO를 충족하지 못하고, 인기 방송이 몰린 partition의 적체가 주원인으로 반복 관측된다.
2. 기존 입력 수준을 넘는 단일 방송 트래픽을 수용해야 하며, 현재 S1과 consumer 병렬화만으로 목표를 만족하지 못한다.
3. 운영 복구에서 한 인기 방송 때문에 다른 방송의 회복 기한이 반복해서 깨지고, DB/외부 원천/수집 버퍼의 전역 병목으로 설명되지 않는다.

#49에서 목표 부하/SLO가 확정되거나 #48에서 다중 broker 환경이 준비되면, A(S1/C1)를 목표 편향 입력으로 실행해 재검토 여부를 확인한다. RF3에서는 consumer lag 외에도 partition별 produce/ACK p99·publisher pending/거절·ISR 축소/복제 부족·leader broker의 네트워크/디스크 편중을 함께 확인한다. 현재 RF1 측정으로 이 신호의 한계를 검증했다고 주장하지 않는다.

초기 진단 문턱은 **실험 재개를 위한 선택값**이며 현재 운영 SLO나 실측 최대가 아니다. 같은 조건 3회 중 2회에서 10분 측정의 마지막 5분 동안 hot partition lag 기울기 >5건/s, 마지막 lag >1,000, 그 partition의 **적체 비중**이 group lag의 80% 이상인지를 먼저 본다. 다른 partition은 마지막 5분의 기울기 ≤1건/s와 종료 lag ≤200인지 함께 본다. 유입/처리율·record 나이·DB lock/pool·WAL·버퍼 나이·시계 유효성을 모두 보존한다. 이 조건만으로 원인을 확정하지 않고, 관측 불가·전역 DB 포화·group 전체 처리율 대비 유입률을 먼저 분리한다. C1 자체의 처리율 부족도 같은 적체 모양을 만들 수 있으므로 B 대조로 구분한다. 적체 비중 문턱은 입력의 80% 편향과 다른 지표다. 실제 목표의 성격에 따라 문턱을 바꾸면 실행 전에 이유를 기록한다.

현재는 전체 제품 S3, hot S3/일반 S1 혼합, 전체 shard 품질, routing 전환·복귀, S3 로그 PITR을 실행하지 않았다. #63의 보존 변경은 [PR #72](https://github.com/joejaeyoung/jigeumini/pull/72)를 통해 develop에 병합됐으며, 도입 재검토는 병합된 보존 계약과 aged DB를 기준으로 한다.

## 재개 시 고정할 대조

| 후보 | 배정·소비 | 목적 |
|---|---|---|
| A | S1/C1 | 현재 제품 기준선 |
| B | S1/C3 | consumer 병렬화의 효과와 비용만 분리 |
| C | hot S3·일반 S1/C3 | B에 더한 라우팅 분산의 효과 |
| D | 같은 혼합 S3/C1 | 병렬 소비 없는 분산의 비용을 확인하는 음성 대조 |

회복 지연 때문에 재개한다면 A~D에 인기 방송 전용 topic/소비 자원의 격리 후보를 추가하고 cold 방송별 회복 시간·미관측을 대조한다. S3가 모든 partition으로 트래픽을 펼치는 영향도 측정한다. 격리의 추가 broker/DB 비용을 자원 예산 밖에 숨기지 않는다.

실행 전 다음 계획을 commit하고 모든 후보에 같은 조건을 적용한다.

- P3/RF1의 로컬 비교부터 시작한다. 전체 분석기·DB·Kafka·생성기 자원과 **총 DB 연결 수**를 고정한다. API 프로세스를 복제해 consumer 수를 바꾸지 않는다. 이후 운영 후보 RF3/장애 영역은 #48/#49에서 따로 확인한다.
- 같은 이미지 기반 코드·JDK/GC·계측 모드·입력 seed·eventId·bytes·중복률·채널 수·관측 주기·API 비율·보존 데이터량을 사용한다. fresh DB와 7일 상당의 aged DB를 별도 집합으로 다룬다. 자원·코드가 다르면 대조에서 제외 이유를 적는다.
- 주 비교는 재개를 일으킨 목표 입력 R이며, 기존 100채널·총 500건/s·API 10요청/s·1KiB·80% 편향은 회귀 대조로 포함한다. 균등 분포는 독립 단계로 추가하고 이전 실패를 덮어쓰지 않는다. 60초 준비 후 10분 측정하며 A/B/C를 ABC→BCA→CAB 순서로 3회 대조한다. D도 두 순서를 포함해 반복한다. 자동 생성기의 지연·승인 실패를 제품 처리 성공으로 세지 않는다.
- 현행 전체 제품 oracle/SLO와 기대 계수를 실행 전에 고정한다. 각 실행에서 전 projection·품질·관측·리포트 귀속·outbox를 대조하고 최종 고정 end를 배출한다. replay CLI의 10초 bucket 비교만으로 전체 제품 정합을 대신하지 않는다.
- 채택 후보 C는 B 대비 **전체 선택 표본의 순위 가시성 p95 중앙값 20% 이상 감소 또는 동일 SLO의 검증된 지속 입력 단계 25% 이상 증가**를 3회 모두 정합/SLO 통과한 집합에서 보여야 한다. 가시성은 receivedAt부터 DB commit 뒤 조회 관측까지이며, 선택 표본에 미관측이 하나라도 있어 전체 선택 p95가 null이면 실패다. 20/25%와 아래 10%는 추가 복잡성을 정당화하기 위해 이번 결정에서 정한 기준이며 측정 결과가 아니다. C와 A도 함께 보고한다. 가시성 표본 누락률·API p95·DB lock/pool/WAL·buffer·자원 비용의 악화를 숨기지 않는다. 같은 입력·자원에서 B 대비 API p95 또는 단위 이벤트당 DB WAL/CPU가 10% 넘게 나빠지면 이 기준의 채택 대상에서 제외하고 원인을 먼저 조사한다.
- 지속 입력의 상향 기준을 쓸 경우 실행 전에 R/2~2R에서 최대 6개 입력률을 고정한다. B와 C를 같은 단계에서 반복하고, B가 3회 모두 통과한 최고 단계보다 25% 이상 높은 단계에서 C의 3회 통과와 B의 실패를 확인한다. 경계를 찾지 못하면 “최대치”나 이 상향 기준의 충족을 주장하지 않고 추가 계획을 먼저 기록한다. 최대 처리율의 연속값 추정과 검증된 단계의 차이를 유지한다.
- steady 구간의 모든 partition lag 기울기 ≤1건/s, 종료 뒤 고정 end 배출, 정상 품질에 대한 오판 0을 요구한다. 입력률 상향 결과가 짧은 backlog 소모인지 확인한다. 채택 전 목표 입력에서 30분 이상 지속과 중단/복구를 추가한다. 이 정도 통과도 외부 운영 최대치를 확정하지는 않는다.

## 제품 구현이 다시 필요할 때 지킬 계약

설계 방향은 [#67 도입 검토](SHARDING_REVIEW.md)를 유지한다. [#69 리뷰에서 이관한 하네스 보완](https://github.com/joejaeyoung/jigeumini/issues/68#issuecomment-6419507424)도 재개 때 적용한다. distributionRequired 표기, hot이 아닌 프로필의 channel0 진단 구분, C4 readiness의 실제 broker member 수, CHANNEL_KEY 외 routing을 무시하는 경로의 guard를 포함한다. 다음 항목은 미구현이며 채택 전 검증 목록이다.

- `ChatRouting`이 업무 key=channelId, eventId 기반 명시 partition, topic identity/P, routing version·불변 정책 이력·기대 partition 집합을 함께 소유한다. `1≤S≤P`이며 여러 producer가 동일 eventId를 재발행해도 같은 정책에서는 같은 배정을 사용한다. 원천 재수신이 새 eventId가 되는 중복은 별도 한계다.
- 소비 실행의 할당·rebalance·종료·진단을 병렬화하되 모든 projection의 전역 eventId 멱등성·payload 충돌·원자 DB/progress·partition별 offset 벡터를 유지한다. 같은 bucket의 잠금 순서와 deadlock/retry·failedAttempts를 측정한다. category/report의 channel advisory lock은 근거 없이 제거하지 않는다.
- 품질은 창에 적용된 모든 정책의 기대 partition **합집합**을 확인한다. 조용한 shard도 포함한다. 한 shard가 멈춤/적체/미관측/blocked이면 정상 순위·급상승·알림을 확정하지 않는다. 늦은 관측, 카테고리 전환, 리포트 보정과 품질 정정을 전체 oracle로 대조한다.
- 전환은 수집 중지→발행 drain→고정 end까지 모든 DB 배출→이전 writer 종료 확인→정책과 offset 벡터 기록 순서다. 부분 실패는 새 writer를 시작하지 않는 상태로 수렴해야 한다. group reset과 과거 로그 재분배는 하지 않는다. 복귀 후에도 과거 S3를 읽는 reader를 보존한다.
- 정책 이력은 보존된 Kafka 로그·DB/PITR 복구 지점이 요구하는 버전을 지우지 않는다. old/new writer 혼재, 전환 중 강제 종료, cross-partition 동일 UUID/충돌, commit 직후 종료·재전달, P 변경 거부/명시 이행, retention gap·PITR 복원을 시험한다.
- 같은 projection을 여러 writer가 처리할 때 보존 하한 잠금·정리 진행과 live 지연도 측정한다. #63의 단일 consumer 정리 결과를 C3의 지속 정리율로 확장하지 않는다.

## 인프라 판단에 미치는 영향

[현재 인프라](../design/INFRASTRUCTURE.md)의 공용 P3와 여섯 group 구성을 유지한다. 방송 수로 토픽 수를 늘리거나 샤딩 개선 배수로 VM 수를 줄이지 않는다. 입력률·편향·채널 관측 비용·DB/WAL/백업/보존을 함께 산정한다.

Kafka RF3/minISR2/전용 controller와 다중 장애 영역은 HA 후보이고, API/분석기·PG의 단일 장애 지점은 별도로 남는다. 운영 공급자·리전·월 예산·실제 SLO/RPO/RTO와 #48/#49 검증이 필요하다. 이번 판단은 운영 SKU나 외부 배포 승인이 아니다.

## 검토 범위

초기 c282cf0의 [Claude 정적 리뷰](../poc/evidence/sharding-decision-2026-10-27/initial-review.json)는 APPROVE였다. 비차단 의견을 보완한 최종 HEAD의 판정은 PR에 별도로 연결한다. Standards/Spec은 참조 hash·기존 수치·미실행 구분을 읽기 전용으로 확인했으며, 새 제품 S3 실험을 수행한 리뷰가 아니다. CI는 성공 전까지 병합 게이트로 유지한다.
