# 치지직 채팅 순위 프로젝트 구현 가능성

확인일: 2026-10-25. 공식 공개 문서와 개발자센터 공개 이용약관을 확인했다. 앱 등록·승인·OAuth 인증·실제 채팅 수신은 실행하지 않았다.

## 판단

**연동에 동의한 방송의 채팅 활동 순위는 조건부로 구현 가능하다. 임의의 모든 방송을 수집하는 전체 채팅 순위는 공식 API 명세로 지원된다고 볼 수 없다.** 기술 구현보다 참여 스트리머 확보가 먼저 해결할 조건이다.

## 문서에서 확인한 사실

- **채팅 수신 API 존재:** `POST /open/v1/sessions/events/subscribe/chat`으로 실시간 이벤트를 구독한다. `채팅 메시지 조회` 권한의 사용자 Access Token이 필요하다. 요청 인자는 `sessionKey`이며 임의의 대상 `channelId` 인자가 없다. 유저 세션은 해당 토큰 사용자 이벤트만 구독한다. 따라서 채널별 사용자 연동이 필요한 구조로 해석된다. [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session)
- **연결 제한:** 클라이언트 인증 연결 최대 10개, 사용자 연결은 유저당 최대 3개, 세션당 이벤트 구독 최대 30개다. 30은 수신 메시지 수 제한이 아니라 채팅·후원·구독의 구독 개수다. 공식 가이드는 Socket.IO-client 1.0.0+부터 2.0.3까지를 명시한다. [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session)
- **채팅 데이터:** 채널 ID, 작성자 ID, 내용, `messageTime` 등이 제공된다. 공개 채팅 이벤트 스키마에는 고유 메시지 ID가 명시되어 있지 않다. [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session)
- **OAuth 유지:** Access Token 1일, Refresh Token 30일이며 Refresh Token은 일회용이다. 갱신 시 새 토큰 쌍을 저장해야 한다. [Authorization](https://chzzk.gitbook.io/chzzk/chzzk-api/authorization)
- **방송 발견:** `GET /open/v1/lives`는 Client 인증으로 전체 라이브 목록을 제공한다. 페이지당 최대 20개, 시청자 수 내림차순이며 현재 시청자 수와 채널 정보가 있다. 이 권한과 채팅 수신 권한은 별개다. [Live](https://chzzk.gitbook.io/chzzk/chzzk-api/live)
- **등록·승인:** 이용약관 제5조는 가입·등록 후 Client ID 발급과 API 이용신청 검토·승인 절차를 규정한다. 승인 소요기간은 확인되지 않았다. 제7조는 복수 Client ID를 이용한 호출 한도 우회와 앱 내 광고 또는 이용 대가 수취를 제한한다. 프로젝트 공개·수익화 범위는 실제 적용 약관을 다시 확인해야 한다. [개발자센터 이용약관](https://developers.chzzk.naver.com/termsDetail)
- **운영 주의:** 공식 참고사항은 429를 Quota 초과로 정의하지만 확인한 공개 문서에는 분당·일당 호출 한도가 없다. 90일간 API Scope 사용량이 없는 앱은 삭제된다. 앱 ID와 이름에는 `chzzk`, `치지직`, `naver`, `네이버`를 넣을 수 없다. [참고사항](https://chzzk.gitbook.io/chzzk/chzzk-api/tips)

## 추론과 미확인 사항

- 공개 Session 명세에는 과거 채팅 조회, 재개 오프셋, 누락 이벤트 재전송 계약이 없다. **연결이 끊어진 동안의 채팅을 나중에 복구할 수 있다고 보장하면 안 된다.** 세션 목록을 90일간 조회할 수 있다는 설명은 채팅 이력 보관 설명이 아니다. [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session)
- 고유 메시지 ID가 없는 명세만으로 원천 이벤트의 완전한 중복 제거를 보장하기 어렵다. 내부에서 만든 이벤트 ID는 수집 이후의 재처리에는 유용하지만 원천 재전송을 식별하지는 못한다.
- Kafka에 이미 적재한 데이터는 보존기간 내 재처리할 수 있다. 반면 수집기와 치지직 사이에서 놓친 데이터는 Kafka로 복구할 수 없다. 화면에 수집 중단 구간을 표시하고 완전한 플랫폼 전체 통계처럼 표현하지 않는 설계가 필요하다.
- 실제 수신량 제한, 구독 중 토큰 만료 영향, 재접속 동작, 승인 시 제공되는 호출 한도는 실증하지 않았다. 여러 토큰을 사용하는 클라이언트 세션의 다채널 구독도 PoC에서 확인해야 한다.

## 권장 진행 조건

1. 개발자센터에 서비스 목적과 최소 권한으로 앱 이용신청 후 승인 가능 여부를 확인한다.
2. 본인 또는 협력 스트리머 계정으로 OAuth 연동하여 실제 채팅 이벤트 수신을 확인한다.
3. 두 채널 연동, 토큰 갱신, 연결 종료·재접속을 검증한 뒤 Kafka 구현을 확대한다.
4. 초기 제품 범위는 **참여 방송의 최근 1분 채팅량·급상승·수집 상태**로 제한한다. 부하 테스트는 생성 이벤트로 수행한다.
5. 협력 스트리머 확보가 어렵다면 공식 Live API의 시청자 수·카테고리 추이를 수집하는 프로젝트로 전환할 수 있다. 단, 이는 채팅 순위가 아니라 시청자 수 추적 서비스다.

등록·승인과 실수신 검증을 먼저 통과하면 진행할 가치가 있다. 전체 방송 채팅 자동 수집이 필수 요구라면 현재 공식 API 기반 기획은 변경하는 편이 합리적이다.
