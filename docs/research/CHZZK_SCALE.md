# 치지직 수집 범위·방송 선정·수집기 확장 조사

조사일: **2026-10-26 KST**. 공개된 공식 개발 문서·개발자센터 약관과 저장소 코드를 읽었다. 앱 등록, OAuth 연동, 공식 API 호출, 공개 방송 대량 조회·채팅 접속은 수행하지 않았다. 아래 공식 규격과 제품 정책 제안, 실제 검증이 필요한 조건을 구분한다. 이 문서는 진행 상태를 관리하지 않으며, 진행 상태 정본은 `docs/STATUS.md`다.

## 1. 결론

**전체 라이브 목록을 발견하는 기능은 공식 API에 있다. 그 목록의 모든 채팅을 수신할 권한이 함께 생기지는 않는다.** 공식 채팅 수신은 사용자 인증·동의 범위를 따른다. 현재 프로젝트의 익명 READ 수집은 다른 비공식 경로이며, 3개 채널 PoC 성공으로 전체 플랫폼 접근·호출 허용량·지속 운영을 증명할 수 없다. [Live](https://chzzk.gitbook.io/chzzk/chzzk-api/live), [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session)

팔로워 수 기준은 구현 가능하다. 채널 정보 API가 합계 `followerCount`를 제공하므로 개인 팔로워 목록은 필요 없다. 그러나 팔로워 1,000명이나 10,000명이라는 수치를 치지직의 공식 수집 허용 기준으로 제시할 근거는 없다. 제품 설정으로 두고, 관측한 후보 수·채팅량·비용·대표성에 따라 선택해야 한다. [Channel](https://chzzk.gitbook.io/chzzk/chzzk-api/channel)

## 2. 공식 문서에서 확인한 계약

| 항목 | 확인한 사실 | 설계에 적용할 의미 |
|---|---|---|
| 방송 발견 | `GET /open/v1/lives`, Client 인증, 페이지당 1~20개, `page.next`로 후속 페이지, 현재 시청자 수 내림차순. `liveId`, `channelId`, 현재 시청자 수, 시작 시각, 성인 여부, 카테고리 제공. | 한 페이지를 전체 방송으로 취급하지 않는다. 페이지 수·완료 여부·조사 시각을 남긴다. [Live](https://chzzk.gitbook.io/chzzk/chzzk-api/live) |
| 팔로워 수 | `GET /open/v1/channels`, Client 인증, 요청당 채널 ID 최대 20개. 응답에 `followerCount`, `verifiedMark`가 있다. 찾지 못한 채널은 결과에 없다. | 최대 20개 단위로 합계만 조회한다. 응답 누락을 팔로워 0명으로 바꾸지 않는다. [Channel](https://chzzk.gitbook.io/chzzk/chzzk-api/channel) |
| 개인 팔로워·구독자 목록 | 별도 조회 API와 사용자 Access Token 권한이 필요하다. | 방송 선정에 사용하지 않는다. 작성자·팔로워 개인 식별정보를 받거나 저장하는 범위를 늘릴 이유가 없다. [Channel](https://chzzk.gitbook.io/chzzk/chzzk-api/channel) |
| 채팅 구독 | `POST /open/v1/sessions/events/subscribe/chat`은 사용자 Access Token의 채팅 조회 권한이 필요하며 인자는 `sessionKey`다. 임의 대상 `channelId` 인자는 없다. 유저 세션은 생성에 사용한 사용자 이벤트만 구독한다. | 채팅 대상 선정 전에 실제 접근 권한을 확인한다. [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session) |
| 연결·구독 수 | 클라이언트 연결 최대 10개, 유저 연결은 유저별 최대 3개. 세션마다 채팅·후원·구독 이벤트를 합쳐 최대 30개 구독. 문서가 명시한 Socket.IO-client 범위는 1.0.0+~2.0.3. | 30은 메시지 초당 처리량이 아니다. 현재 일반 WebSocket 수집기에 공식 세션 URL만 바꿔 끼울 수 없다. [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session) |
| 인증 | Client API는 `Client-Id`/`Client-Secret` 헤더, 사용자 API는 Bearer Access Token을 사용한다. | 브라우저에서 Client Secret으로 직접 호출하지 않는다. 서버 어댑터·비밀값 주입 경계를 둔다. [참고사항](https://chzzk.gitbook.io/chzzk/chzzk-api/tips) |
| 토큰 수명 | Access Token 1일, Refresh Token 30일이며 Refresh Token은 일회용이다. 등록한 redirect URI와 인증 요청 URI가 일치해야 한다. | 공식 수신의 장기 운영은 갱신 경쟁·재인증·동의 철회를 처리해야 한다. 지금의 메모리 토큰 PoC와 다른 작업이다. [Authorization](https://chzzk.gitbook.io/chzzk/chzzk-api/authorization) |
| 요청 한도 | 공개 참고사항은 429를 Quota 초과로 설명한다. 조사한 공식 페이지·검색에서는 정확한 분당·일당 허용량과 quota의 적용 단위를 확인하지 못했다. | 임의 RPS를 공식 한도로 기록하지 않는다. 승인된 설정을 입력받고, 429는 호출 축소·유예 사유로 처리한다. [참고사항](https://chzzk.gitbook.io/chzzk/chzzk-api/tips) |

세션 슬롯을 단순 계산하면 클라이언트 연결 풀은 `10 × 30 = 300`개 이벤트 구독이다. **이것은 문서상 제한을 곱한 추론**이며, 서로 다른 사용자 토큰을 통한 다채널 구독이 실제로 성공한다는 실측이나 서비스 전체의 최대 채널 수가 아니다. 유저별 연결 경로와도 구분해야 한다. 다채널 사용 방식·승인 범위는 개발자센터 확인과 소규모 실제 연동으로 검증한다. [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session)

채팅 이벤트 명세에는 작성자 정보·본문·시각이 있으나 원천 메시지 고유 ID와 재개 offset/과거 이력 재전송 계약은 확인되지 않는다. 따라서 연결 정상 시간이나 Kafka 적재 성공을 원천 채팅의 무손실 수신으로 표현하지 않는다. [Session](https://chzzk.gitbook.io/chzzk/chzzk-api/session)

## 3. 이용신청과 외부 확인이 필요한 범위

개발자센터 약관 제5조는 앱 등록에 따른 Client ID 발급과 API 사용 신청·검토·승인을 설명한다. 제7조에는 동일 목적의 다수 Client ID로 허용량을 늘리는 행위, 광고 삽입 또는 앱 이용 대가 수취에 관한 제한이 있다. 공식 API 사용 표시 의무도 있다. 전체 채널 수집을 위해 앱 ID를 쪼개는 방식을 설계하지 않는다. 실제 서비스 목적·공개 범위에 적용할 조건은 운영 전에 확인한다. [개발자센터 이용약관](https://developers.chzzk.naver.com/termsDetail)

약관 페이지는 JavaScript 화면이어서 웹 도구의 본문 추출 결과는 빈 앱 셸이었다. 같은 공개 페이지가 로드하는 공식 정적 번들에서 제5조·제7조 문구를 재확인했다. 계정 로그인이나 내부 API 호출은 하지 않았다. 조사 시 제공된 번들: [main.16e89f8a.js](https://ssl.pstatic.net/static/nng/glive-open/resource/p/static/js/main.16e89f8a.js). 위 내용은 운영 의사결정을 위한 문서 요약이며 비공식 READ 접속의 허용 여부를 판정한 결과가 아니다.

외부에서 확인할 질문은 다음처럼 구체화한다.

1. 공개 방송 목록의 전체 페이지 순회 목적, 간격, 승인된 호출 허용량과 적용 단위는 무엇인가?
2. 여러 연동 스트리머를 클라이언트 세션에 구독하는 방식과 동시 구독 상한은 어떻게 적용되는가?
3. 개인정보·원문을 즉시 버리고 집계 수치만 제공하는 공개 분석 서비스가 승인 목적에 부합하는가?
4. 비공식 익명 READ 경로를 사용하는 현재 PoC를 운영 수집으로 확대할 수 있는 근거가 있는가? 없다면 공식 연동 방송으로 범위를 제한할 것인가?
5. 증설/호출량 협의 절차가 있는가? 공개 문서에는 협의 결과나 보장량이 없으므로 계정 화면·공식 문의 결과를 별도 근거로 남긴다.

개발자센터 이용에는 계정이 필요하고, 단체 ID를 쓰는 법인은 비즈니스 채널 승인 절차가 안내되어 있다. 에이전트가 임의 계정 생성·약관 동의·제3자 문의를 대신 진행할 작업으로 취급하지 않는다. [개발자 센터 안내](https://help.naver.com/service/30044/contents/23939?lang=ko&osType=COMMONOS)

## 5. 스트리머 선정 정책 제안

다음은 **제품 설계 제안**이다. 공식 제한이나 이미 합의된 운영 수치가 아니다.

### 입력과 제외 조건

- 목록 어댑터는 채널/방송 ID, 시청자 수, 시작 시각, 접근 제한 여부, 카테고리만 정규화한다. 방송 제목·채널명·이미지 URL·태그는 선정 이력에 보관하지 않는다.
- 채널 어댑터는 `followerCount`와 값의 관측 시각만 추가한다. 개인 팔로워/구독자 목록은 호출하지 않는다.
- `sourceMode`를 `OFFICIAL_AUTHORIZED` / 기존 `UNOFFICIAL_POC`처럼 구분한다. 채널을 발견한 것과 채팅 수신 가능 여부를 같은 bool로 합치지 않는다.
- 적격 조건은 현재 라이브, 제한 없음, 선택한 소스에서 접근 가능, 메타데이터 유효기간 충족이다. 철회/제한/운영자 제외는 재선정 대기 없이 제거한다.
- 값이 없거나 만료되면 unknown으로 분류한다. 팔로워/시청자/접근 가능 여부를 0 또는 true로 보정하지 않는다.

### 정책 파라미터

| 설정 | 제안하는 계약 |
|---|---|
| `minFollowers` | 선택적 0 이상 정수. 미설정이면 팔로워 cutoff 없음. 양수 설정 시 값 미확인 채널은 `FOLLOWERS_UNKNOWN`으로 제외. 경계는 `followerCount >= minFollowers`. |
| `maxChannels` | 수집 연결·버퍼·발행/DB 용량에 따른 명시적 양수 상한. PoC의 3개 제한은 별도 유지. 선정 dry-run의 수가 자동 live 연결 수가 되지 않음. |
| `maxPages`, `scanDeadline`, `requestBudget` | 목록 순회 자체의 비용 상한. 끝까지 못 읽으면 `scanComplete=false`. 승인된 실제 한도가 없을 때는 합성 fixture 실행이 기본. |
| `metadataTtl`, `selectionVersion` | 값의 신선도와 정책 변경 시점을 재현하기 위한 정보. TTL 만료를 방송 종료로 해석하지 않음. |
| `minResidence`, `replacementMargin` | 시청자 순서가 조금 흔들릴 때 잦은 연결 교체를 막는 후보 정책. 접근권 철회·제한·명시적 종료는 이 대기 조건보다 우선. |
| `excludedChannels` | 운영자가 제외한 공개 방송 ID 목록. 제외 사유 코드는 고정값만 기록하고 자유 입력/개인정보는 이력에 싣지 않음. |

최초 구현은 deterministic dry-run으로 `minFollowers = 미설정 / 1,000 / 5,000 / 10,000` 후보를 비교할 수 있다. 이 숫자들은 **민감도 분석용 가상 시나리오**이며 운영 권고값이 아니다. 같은 입력에서 적격 수, 카테고리별 선정 비율, 예상 연결 수, 실측 가능한 경우 수신율을 비교한 뒤 값을 결정한다. 실제 분포를 아직 보지 않았으므로 지금 특정 팔로워 수를 정당화할 수 없다.

용량이 부족하면 적격 채널을 현재 시청자 수 → 팔로워 수 → 공개 채널 ID 순으로 안정 정렬하여 상한만큼 선정하는 간단한 정책부터 재현 가능하게 구현한다. 상위 방송 중심 표본이라는 편향을 공개한다. 장르별 몫/작은 채널 탐색은 별도 정책 버전으로 비교할 수 있지만, 근거 없이 균등 표본이나 전체 대표성을 주장하지 않는다. 팔로워 수는 누적 인기이고 현재 채팅 부하의 측정값이 아니므로 Kafka 용량을 팔로워 수만으로 산정하지 않는다.

## 6. 발견 범위와 수집 품질을 별도 숫자로 표시

공식 목록은 현재 시청자 순서와 cursor를 명시하지만, 여러 페이지를 읽는 동안 동일 시점의 고정 snapshot이라는 보장은 찾지 못했다. 방송 시작/종료·순위 이동으로 중복이나 누락이 생길 수 있다는 것은 이 계약에서 도출한 **설계상 가능성**이다. `channelId + liveId`를 기준으로 중복을 제거하고, 페이지 반복·cursor 순환·기한/호출 상한 초과를 탐지한다. 순회를 끝냈더라도 표현은 “해당 순회에서 발견한 방송”으로 제한한다. [Live](https://chzzk.gitbook.io/chzzk/chzzk-api/live)

권장 응답은 다음 단계의 수와 기준 시각이다.

| 값 | 의미 |
|---|---|
| `discovered` | 이번 scan에서 중복 제거 후 발견한 방송 수 |
| `eligible` | 소스 접근 가능·정책 조건을 충족한 수 |
| `selected` | 용량 상한 안에서 선택한 수 |
| `assigned` | 실제 수집 worker에 소유권을 할당한 수 |
| `connected` | 연결 상태 관측이 유효한 수 |
| `healthyWindow` | 기존 품질 계약으로 해당 집계 창이 정상인 수 |
| `exclusionCounts` | 접근 제한/동의 없음/팔로워 미달/값 미확인/용량 제한 등 상호 배타적인 주 사유별 수 |
| `scanComplete`, `scanStartedAt`, `scanFinishedAt`, `scanAge` | 발견 자체의 최신성과 부분 결과 여부 |

- `selected / eligible`: 선정 용량 충족률. 전체 치지직 수집률이 아니다.
- `healthyWindow / selected`: 선정 방송의 정상 관측 비율. 메시지 수신율이 아니다.
- `selected / discovered`: 이번 관측 목록 대비 선정 비율. 부분 scan에서는 전체 coverage로 표시하지 않는다.
- 0분모는 비율 `null`과 원인을 반환한다. 0%·100%를 임의 생성하지 않는다.
- scan 실패가 모든 채널 OFFLINE으로 번지지 않게 마지막 성공 계획을 제한된 TTL 동안 유지한다. 새로운 접근권 철회·명시적 종료는 이 유지 규칙과 별도로 즉시 반영한다. TTL 이후는 `UNKNOWN`/`STALE`이며 채팅 0건이 아니다.
- 사용자 문구는 “선정한 방송 20개 중 18개 정상 수집 · 목록 확인 시각 …”처럼 쓴다. Kafka 파티션이나 OAuth token 상태를 일반 화면에 노출할 필요는 없다.

이 정의들은 기존 분 단위 연결 coverage와 별개의 표본 범위 지표다. 두 숫자를 동일한 `coverage` 필드로 합치지 않는다.

## 7. API 호출 예산과 수집기 용량 산정

아래 계산은 자체 비용 모델이며 실제 허용량이나 실측치가 아니다.

```text
N = 순회에서 발견한 라이브 수
U = 팔로워 합계 캐시가 없거나 만료된 채널 수
P = 실제 읽은 라이브 페이지 수 (이상적 최소 ceil(N / 20))
C = 채널 합계 조회 요청 수 (ceil(U / 20))
HTTP 요청/scan ≈ P + C + 재시도 요청
지속 요청률 ≈ 실제 요청 수 / 실제 scan 간격

Kafka 수신률 λ = 선정 채널별 실측 일반 채팅 events/s 합계
하루 정규화 입력 bytes ≈ λ × 평균 직렬화 bytes × 86,400
```

페이지 최대 20와 채널 배치 최대 20의 근거: [Live](https://chzzk.gitbook.io/chzzk/chzzk-api/live), [Channel](https://chzzk.gitbook.io/chzzk/chzzk-api/channel). 예를 들어 가상의 2,000개 라이브를 한 번 읽고 모두 채널 합계를 갱신하면 최소 약 200요청이다. 이것을 1분마다 허용받았다는 뜻은 아니다. 일괄 조회와 TTL 캐시로 요청을 줄인 뒤 승인된 호출 예산 안에 맞춘다.

수집 worker 수는 연결 수뿐 아니라 `수신 events/s`, parse CPU, 이벤트 크기, buffered+in-flight 수/나이, Kafka ACK 지연으로 결정한다. 편중 채널 한 곳이 전체 용량을 차지할 수 있으므로 채널별 공정성과 상한을 관측한다. Kafka와 DB의 저장비는 복제·인덱스·WAL·ledger·여러 projection·보존기간을 별도로 합산해야 한다. 이 계산만으로 HA나 24시간 운영 용량을 확정하지 않는다.

## 8. 등록 가능한 구현 이슈 단위

모든 AFK 항목은 코드·합성/로컬 통합 검증·한국어 결정 문서·이슈별 리팩토링 점검·작업 로그를 완료 조건으로 포함한다. 실제 자격증명·승인 제공 전에도 진행할 수 있다.

### A. 공식 방송 발견·선정 dry-run과 범위 표시 — AFK

- **구현:** 공식 Live/Channel HTTP 어댑터, 허용 필드만 남기는 응답 변환, 설정 가능한 선정 규칙, API/UI의 선정 범위·기준 시각 표시.
- **검증:** 여러 페이지, 중복 항목, 반복 cursor, 잘못된 JSON, 429/5xx, 초과 기한, 팔로워 경계, 누락 값, 성인/제한, 동일 입력의 안정 순서, 상한 제외 이유, 0분모를 fixture 서버로 검증. 원문 응답·비밀 헤더를 로그에 남기지 않는지 확인.
- **완료 근거:** 합성 입력 manifest와 선정 결과, 호출 수/scan 상태, 화면 검증. 자격증명이 없을 때 실제 호출 성공으로 기록하지 않음.
- **기술 연결:** 새 수집 범위 목표(신규 T 번호) + 기존 T08/T11의 용량 신호. 제품 기능이므로 Kafka 성과로 모두 계산하지 않음.

### B. 수집 worker 할당·인계·재접속 동시성 제어 — AFK

- **구현:** 선정 계획을 worker 소유권으로 바꾸는 작은 계약, lease/epoch, 만료 시 발행 차단과 연결 종료, 제한된 연결 시작 속도, graceful handoff, 공백 원인 기록.
- **검증:** 합성 WebSocket으로 두 worker 경쟁, owner 종료, 장시간 정지 후 복귀, lease 갱신 실패, 네트워크 분리, 선정 변경, 토픽/DB 지연을 주입. 소유권 없는 worker가 발행하지 못하는지 실제 경계에서 확인.
- **주의:** lease row 하나만 추가했다고 이중 수신이 완전히 방지되는 것은 아니다. 오래된 worker가 계속 살아 있을 때 발행을 막는 fencing 경계가 필요하다. 수집기 간 동일 원천 메시지 판별은 현재 랜덤 UUID로 해결되지 않는다. 인계 중 source 공백/중첩 가능성과 Kafka 이후 멱등성을 분리해 결과에 적는다.
- **기술 연결:** 신규 수집 소유권 목표 + T02/T11/T12. 무손실·원천 Exactly-once를 완료 조건으로 쓰지 않음.

### C. 승인된 공식 채팅 어댑터·인증 수명 관리 — AFK 구현 + HITL 실검증

- **독립 구현 가능:** Socket.IO 호환 adapter seam, 구독 슬롯 계획, 합성 SYSTEM/CHAT fixture, 동의 철회·토큰 만료·재구독 상태 전이, 비밀값 redaction, 기존 최소 이벤트로 변환.
- **외부 입력 필요:** 개발자 앱 승인, Client 자격증명, 협력 스트리머의 OAuth 동의, 실제 다채널 구독·갱신 검증.
- **현재 규칙과의 경계:** 토큰을 저장하지 않는 프로젝트 규칙이 있다. 장기 refresh 저장소를 임의 도입하지 않는다. 우선 메모리/외부 주입으로 검증하고, 운영 비밀값 저장 방식은 사용자와 명시적으로 정한 별도 계약이 필요하다.
- **완료 분리:** 합성 adapter 구현 완료와 공식 운영 연동 완료를 별도 체크한다. 계정이 없다고 합성 구현을 기다릴 필요는 없지만, 실제 연동까지 확인한 것으로 issue를 닫지 않음.

### D. 실제 수집 범위 확대와 운영 승인 확인 — HITL

- **선행:** A/B, Kafka/DB 용량·HA 시험, 배포/관측/복구 리허설.
- **외부 입력:** 운영할 소스 방식, 승인된 호출량·범위, 계정/협력 방송, 비용·운영 환경. 공개 서비스의 약관 적용과 비공식 경로 확대 가능 여부 확인.
- **실행:** 승인된 범위에서 단계별 채널 수·시간을 정해 실수신/ACK/DB 반영, 재접속, 신선도, 저장 증가를 기록. 대량 공개 채널을 부하 생성기로 쓰지 않음.
- **완료:** 실제 날짜·채널 수·입력량·선정 조건·관측 누락·미검증 범위를 남김. 계정이나 승인 없이 “전체 방송 수집 준비 완료”로 대체하지 않음.

## 9. 조사 한계

- 공식 API 응답, 페이지 순회 전체성, 다채널 구독, 최대 구독 슬롯, 토큰 갱신, quota 헤더/Retry-After 제공 여부를 실제 요청으로 확인하지 않았다.
- 현재 방송 수, 팔로워 분포, 채널별 채팅량, 성인·제한 방송의 비율을 측정하지 않았다.
- 문서에 없는 제한이 없다는 뜻이 아니다. Client/사용자/IP/앱별 quota 단위, burst 제한, 서비스 협의 가능 여부는 미확인이다.
- 공개 목록이 모든 제한 방송까지 반환하는지, 정렬 변화 중 cursor가 어떤 일관성을 제공하는지는 보장 문구를 찾지 못했다.
- source 연결이 정상이어도 서버가 누락한 메시지를 현재 이벤트 계약으로 모두 탐지할 수 있는 것은 아니다. Kafka HA는 수집 전 구간의 누락을 복구하지 못한다.
- 이 조사에서는 계정 생성·외부 문의·제3자 메시지 송신·live 수집·외부 배포를 하지 않았다.
